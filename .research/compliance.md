## 1. Supabase (verified from supabase.com/docs unless noted)

Regions (specific AWS regions; the project's DB, Auth and Storage sit in that one region)
- https://supabase.com/docs/guides/security/gdpr-compliance : pick a *specific* EU region; the general "Europe" group also includes London and Zurich (non-EU).
- https://supabase.com/docs/guides/functions/regional-invocation lists eu-central-1 Frankfurt, eu-west-1 Ireland, eu-west-2 London, eu-west-3 Paris.
- Management API / MCP create_project enum also offers eu-central-2 (Zurich) and eu-north-1 (Stockholm). The /regions page itself renders the list dynamically (not in text).
- Supabase offers a DPA: https://supabase.com/legal/dpa . Docs say backups, logs, Edge Functions and sub-processors affect the transfer analysis.

Free tier and Pro (https://supabase.com/docs/guides/platform/billing-on-supabase, .../free-project-pausing, .../storage/serving/bandwidth)
- Free: 2 active projects (paused ones do not count); 500 MB DB per project; 50,000 MAU; egress 5 GB (the bandwidth page says 10 GB = 5 cached + 5 uncached; the billing table says 5 GB, so treat the exact figure as in flux); 1 GB storage; 500k edge function invocations.
- Pause: Free projects with low activity over 7 days are paused; warning email ~1 week before; restorable for 90 days from dashboard; "a few user requests to the database each day" keeps it alive. Paid projects never pause.
- Pro: $25/month per organization (shown as "Pro Plan $25" in the invoice examples at .../manage-your-usage/custom-domains), includes 100,000 MAU, 8 GB DB disk/project, 250 GB egress, 100 GB storage, plus compute (a Small project is $15/mo, offset by $10 compute credits).

Auth
- Email+password and magic link/OTP are enabled by default (https://supabase.com/docs/guides/auth/auth-email-passwordless). signInWithOtp auto-signs-up unless `shouldCreateUser: false`; magic link: one request per 60 s default.
- Email confirmation: ON by default for hosted projects (OFF in local dev). Turn off in Dashboard > Authentication > Sign In / Providers > Email > "Confirm email" (https://supabase.com/docs/guides/auth/testing-auth-flows). Caveat from that page: off means anyone can sign up with an address they do not own, and the hourly email limit is also disabled. The production checklist says to enable confirmations.
- Default (built-in) SMTP: sends ONLY to addresses of your org's team members (others fail "Email address not authorized"), heavily rate limited ("subject to change"; the number is injected by config, in the docs historically 2/hour), no SLA, not for production. Custom SMTP needed for any real users (https://supabase.com/docs/guides/auth/auth-smtp). After enabling custom SMTP the starting limit is 30 emails/hour, adjustable at Authentication > Rate Limits. Other limits: 360 OTPs/hour, 60 s between sends to same user.
- Minimum-age setting: I found NONE in the Auth docs. Age gating must be done in the app (e.g. date of birth / age-band field plus guardian consent flow, RLS or a check).

RLS basics (https://supabase.com/docs/guides/database/postgres/row-level-security; text not fetched, standard pattern from memory)
- `alter table t enable row level security;` then `create policy "own rows" on t for select to authenticated using ((select auth.uid()) = user_id);` with `with check` for insert/update. Without policies, RLS-enabled tables return no rows. Production checklist: RLS on every table in exposed schemas. Wrapping `auth.uid()` in `(select ...)` is the recommended performance form.

Verifying a JWT in a Node serverless function
- Simplest, official: `const { data:{user}, error } = await supabase.auth.getUser(jwt)` (shown with the token taken from the `Authorization: Bearer` header, https://supabase.com/docs/guides/functions/auth-legacy-jwt). It always makes a network call to the Auth server; the anon/publishable key is enough, no service key needed.
- Faster: `supabase.auth.getClaims()` (https://supabase.com/docs/reference/javascript/auth-getclaims): verifies the JWT against `/.well-known/jwks.json` (cached) when the project uses asymmetric signing keys (ECC/RSA); with a legacy shared-secret project it falls back to a server request like getUser. Manual alternative: verify with `jose` against `https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` (or HS256 with the legacy JWT secret). Check `aud`=authenticated, `exp`, take `sub` as user id.
- To make queries obey RLS in the function: `createClient(URL, ANON_KEY, { global: { headers: { Authorization: req.headers.authorization } } })`. Never expose the service-role key to the browser; it bypasses RLS.

supabase-js v2 basics (reference: https://supabase.com/docs/reference/javascript/start; syntax standard)
- `createClient(url, anonOrPublishableKey)`; `auth.signUp({email,password,options:{emailRedirectTo,data:{...}}})`; `auth.signInWithPassword({email,password})`; `auth.signInWithOtp({email,options:{shouldCreateUser,emailRedirectTo}})` then `auth.verifyOtp({email,token,type:'email'})` for codes; `auth.onAuthStateChange((event, session)=>{})`; `auth.signOut()`.
- Data: `from('t').select('*').eq('id',x)`, `.upsert({...},{onConflict:'id'})`, `.delete().eq(...)`, `.insert()`; `rpc('fn_name',{arg:1})`. All return `{data,error}`.
- New projects use `sb_publishable_...` keys in docs; legacy anon JWT keys still exist.

Programmatic project creation
- Management API: `POST /v1/projects` (https://supabase.com/docs/reference/api/v1-create-a-project); needs a personal access token (https://supabase.com/dashboard/account/tokens).
- Supabase MCP `create_project` (name, region, organization_id) exists. Its description: "can add to the organization's bill. The user must agree to any nonzero quoted cost before the project is created ... A project quoted at $0 may be created without a cost-confirmation form." So a free-tier ($0) project needs no confirmation form; a paid one needs a confirm_cost_id. Note the 2-active-free-project cap. MCP is "public alpha" per the features table.

## 2. GDPR, school app with minors [UNVERIFIED: gdpr-info.eu was unreachable; check https://gdpr-info.eu/art-8-gdpr/ etc.]

- Art 8(1): where consent (Art 6(1)(a)) is the basis for "information society services offered directly to a child", processing is lawful if the child is at least 16; below that, only with consent authorised by the holder of parental responsibility. Member States may lower it, "provided that such lower age is not below 13 years". Art 8(2): controller must make reasonable efforts to verify parental consent.
- Bulgaria: recollection is 14 (ZZLD, Art 25v / '25c'). No primary text fetched (lex.bg, dv.parliament.bg blocked). Only secondary: gdprlocal.com/digital-age-of-consent-under-the-gdpr/ says Art 25c ZZLD lets children 14+ consent. Verify at https://dv.parliament.bg or https://cpdp.bg (current ZZLD wording) before citing.
- Lawful basis for a school deployment: consent is a poor fit (power imbalance, Recital 43). Usual bases: Art 6(1)(e) public task (state/municipal schools, task set in education law) - the school is the controller; Art 6(1)(b) contract (private schools with the family); Art 6(1)(f) legitimate interest is NOT available to public authorities performing their tasks (Art 6(1) last sentence) and weak for children (Recital 38, balance with child's interests). An app vendor selling directly to pupils/parents would rely on consent or contract.
- Special care for children (Recital 38, 58); Art 25 privacy by design/default; Art 35 DPIA likely (children = vulnerable subjects, voice recordings = possibly biometric if used for identification, which it should not be).
- Minimisation (Art 5(1)(c)) and storage limitation (5(1)(e)): store derived metrics, not raw audio/video, where possible; pseudonymous IDs; no names in prompts to LLMs; short retention; no analytics/ad trackers.
- Erasure (Art 17): must delete on request/when no longer needed; Art 17(1)(f) specifically covers data collected from a child under Art 8(1) - weight given to the data subject being a child. Build delete-account + delete-recordings endpoints; cascade to processors and backups schedule.
- Art 28: when the school/controller uses processors (Supabase, Anthropic, Netlify) there must be a binding contract/DPA covering: documented instructions, confidentiality, security (Art 32), sub-processor authorisation and flow-down, assistance with data-subject rights, breach notice, deletion/return at end, audit rights. If you (the app vendor) are the processor for schools, you need a DPA with each school and your own sub-processor DPAs. Third-country transfers (US providers: Anthropic, possibly Netlify, Supabase corporate) need Chapter V tools: SCCs or the EU-US Data Privacy Framework certification of the provider, plus transfer impact assessment. Supabase DPA: https://supabase.com/legal/dpa .
- Google Fonts / CDNs: LG Munchen I, 20 Jan 2022, Az. 3 O 17493/20 - a website operator embedding Google Fonts from Google servers transmitted the visitor's dynamic IP address to Google (US) without consent; court held IP is personal data, no legitimate interest because fonts can be self-hosted, awarded EUR 100 damages and an injunction. It is a first-instance German judgment, not binding EU-wide, but widely followed in practice. Practical rule: self-host fonts and scripts (no third-party CDN calls) for a school/minor audience. Source to verify: https://www.gesetze-bayern.de (LG Munchen I, 3 O 17493/20).

## 3. EU AI Act Art 5(1)(f) [STILL UNVERIFIED on 2026-11-06 retry: artificialintelligenceact.eu and eur-lex.europa.eu both still failed DNS (ENOTFOUND) despite the allowlist message; quotes below are from memory; verify at https://artificialintelligenceact.eu/article/5/ , /article/3/ , /recital/18/ and EUR-Lex Reg (EU) 2024/1689]

Art 5(1)(f) (prohibited):
> "the placing on the market, the putting into service for this specific purpose, or the use of AI systems to infer emotions of a natural person in the areas of workplace and education institutions, except where the use of the AI system is intended to be put in place or into the market for medical or safety reasons;"

Art 3(39): "'emotion recognition system' means an AI system for the purpose of identifying or inferring emotions or intentions of natural persons on the basis of their biometric data".
Art 3(34): "'biometric data' means personal data resulting from specific technical processing relating to the physical, physiological or behavioural characteristics of a natural person, such as facial images or dactyloscopic data".
Recital 18 (gist, quoted fragments): emotions "such as happiness, sadness, anger, surprise, disgust, embarrassment, excitement, shame, contempt, satisfaction and amusement"; it "does not include physical states, such as pain or fatigue"; nor "the mere detection of readily apparent expressions, gestures or movements, unless they are used for identifying or inferring emotions". Examples of readily apparent expressions: a frown, a smile, hand/arm/head movements, or "characteristics of a person's voice, such as a raised voice or whispering".
Timing: Art 113 - Chapters I and II (incl. Art 5) apply from 2 February 2025; penalties for Art 5 breaches up to EUR 35m / 7% (Art 99(3), applicable from 2 Aug 2025). Commission Guidelines on prohibited practices (4 Feb 2025) say the education ban covers pupils and students, and that voice-based inference counts when it targets emotions; learning-related states like "engagement/attention" they discuss as borderline - read the guidelines.

Assessment (my reasoned opinion, not legal advice). Test: (i) does the system infer an emotion/intention (ii) from biometric data (voice and face are) (iii) in an educational setting. Output labels matter more than the signal.
(a) "Confidence" score from pitch/volume stats: HIGH RISK / likely prohibited. Confidence/nervousness is an inner emotional state in the Recital 18 sense (close to excitement, embarrassment, shame); inferring it from voice features is exactly "inferring emotions from biometric data". Do not ship in schools.
(b) "Expressiveness" score from pitch/volume variability: BORDERLINE, leaning permissible only if it is defined and presented as a purely acoustic measure ("pitch variation: 3.2 semitones") with no emotional label. A score called "expressiveness" invites the reading that it measures emotional expression; Recital 18 exempts mere detection of voice characteristics, but "unless used to infer emotions". Safer: show raw variability without a composite emotional claim, or drop.
(c) AI read of body language / stage presence from video frames: LIKELY PROHIBITED if the model describes feelings (nervous, confident, engaged); video of body is biometric data in the broad Art 3(34) sense, and "stage presence" is an inferred affective/personality judgement. Only mechanical, readily apparent facts (e.g. "hands visible", "looked toward camera x% of time") might fall under the exemption, and even then risk creeping into inference. Avoid video emotion analysis in school mode; no emotion words.
(d) Words per minute, pause lengths, pitch range, volume range, filler-word count: LOW RISK / not emotion recognition. These are objective delivery measures; no emotion or intention is inferred. Note filler words/WPM come from transcription (speech content), not even biometric inference. Keep UI wording factual ("pace", "pauses"), do not map them to "nervous"/"confident", and do not let an LLM feedback prompt add emotional readings.
Design guidance: avoid emotion vocabulary in UI, prompts and docs; make LLM coaching say only what the measures show; keep a documented purpose statement (skills coaching, not emotion inference); a safety/medical exemption does not apply to coaching. Other AI Act points: such a school tool may also be "high risk" under Annex III point 3 only for admission, assessment of learning outcomes, steering learning, or proctoring - keep grading out of it. Art 4 AI literacy duty applies from 2 Feb 2025; transparency duties Art 50 from 2 Aug 2026.
